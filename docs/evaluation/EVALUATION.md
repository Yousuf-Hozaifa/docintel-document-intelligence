## 1. Read this first

- **All data is synthetic and generated by the same author as the extractor** (`eval/make_dataset.py`). The numbers below are an **upper bound** for real invoices: the layouts, labels and number formats were designed by me, so a high score shows the system handles *those* variations, not that it generalises to arbitrary documents. No real invoices were available; none were used.
- Protocol: `dev` (101 invoices) was used to debug and to choose one threshold. `test` (seed 202) was run **once, first, on frozen code** (commit `1986728`) before any fix derived from it. After inspecting its errors I added word-level OCR confidence (section 5.4); because `test` was then inspected, that change is evaluated on a **fresh split `test2`** (seed 303) that was never inspected. Rerunning `test` with the new rule is shown only as a labeled post-hoc row.
- Environment (all runs): Linux-6.18.44-fc-v185-x86_64-with-glibc2.39; Intel(R) Xeon(R) Processor @ 2.10GHz; 1 core(s); 3995 MB RAM; Python 3.12.3; PyMuPDF 2.0; tesseract 5.3.4. Jobs ran one at a time. **This is not the target Windows / 8 GB machine; timings will differ there.**
- Sample sizes are small (about 200 invoices per held-out split, 3–60 invoices per file type). Intervals are 95% Wilson intervals; treat subgroup numbers as indicative.

## 3. Dataset and metric definitions

`test`: 174 files (156 valid, 18 deliberately broken), 199 labeled invoices. `test2` has the same composition with a different seed; `dev` is a 40% sample. Valid files by type: csv 8, jpg 8, pdf+register 14, pdf-digital 59, pdf-scanned 14, png 8, png-degraded 18, tiff 6, xls 6, xlsx 12, xlsx-register 3.

Variation: three invoice layouts (different labels: Invoice Number / Inv # / Invoice No.; Bill To / Sold To; Tax / VAT / GST; Total / Amount Due / Total Amount), supplier as a labeled or unlabeled first line, 5 date formats, 3 invoice-number formats, thousands separators, `$`/`£` symbols or ISO codes, 2–6 line items, multi-invoice PDFs/TIFFs/workbooks (multi-sheet), CSV with `,` `;` tab delimiters, one-invoice-per-row Excel registers, scans at 200 dpi, blurred / half-resolution / 2°-rotated images, missing fields, ambiguous dates, tampered totals, line-arithmetic errors, duplicate and cross-document pairs, and corrupt / empty / encrypted / unsupported / mislabeled / blank files.

**Metrics.** *Exact match*: value equals the label exactly (amounts compared as decimals; dates as ISO; text after trimming). *Precision* = correct ÷ values the system produced; *recall* = correct ÷ values present in the label; *exact-match accuracy* = matches ÷ all field instances, counting a correct “absent” as a match. *Line item* is correct only if description, quantity, unit price and amount all match. *Success* = the file reached `completed`/`partial` with at least one invoice; *failure* = it ended `failed`. Predicted and labeled invoices are paired by invoice number (fallback: order).

**Not covered (generator limits):** euro-symbol invoices (the PDF font cannot draw €), non-English text, handwriting, stamps/logos/background noise, skew above 2°, multi-column or wrapped table layouts, discount/shipping lines, tax-inclusive pricing, real scanner artefacts, PDFs mixing images and text layers.

### 5.5 Is the confidence score calibrated?

No. Field `confidence` is a heuristic (rule strength × OCR word confidence), **not** an empirically calibrated probability. Observed accuracy per confidence bin on `test2` (current code):

| confidence bin | fields | mean stated confidence | observed accuracy |
|---|---|---|---|
| 0.00-0.50 | 119 | 0.387 | 0.958 |
| 0.50-0.70 | 20 | 0.562 | 0.85 |
| 0.70-0.85 | 207 | 0.808 | 1.0 |
| 0.85-0.95 | 1120 | 0.89 | 1.0 |
| 0.95-1.00 | 105 | 0.95 | 1.0 |

Accuracy does not increase monotonically with the stated confidence; but stated confidence is below observed accuracy in every bin, so it is not a probability. In the first `test` run (page-level OCR factor, before word-level confidence) the misread invoice numbers sat in the 0.70–0.85 bin together with correct values (observed accuracy 0.961 over 154 fields), i.e. the score did not separate them; with word-level OCR confidence the weakly read values now fall into the lower bins above. The review decision relies on the validation rules above, not on this number.

## 6. Generalisation check (dev vs held-out)

`dev` (used for debugging) header exact match 99.4%, invoices fully correct 92.1%; `test` 99.5% / 94.0%; `test2` 99.4% / 92.0%. Dev-guided fixes before the first `test` run: label+column-gap separators in spreadsheets, CSV delimiter detection by line statistics, retaining line items whose OCR'd quantity is unreadable. Dataset/scoring bugs I found and fixed on dev: spreadsheets without a printed currency, expected-rule key mismatch, and a false-review metric that counted correctly-flagged duplicates. The similarity of dev and held-out numbers means there is no sign of overfitting *to this generator*; it says nothing about real invoices.

## 7. Limitations and what was not measured

- Synthetic data from one author → optimistic; real-world accuracy is unknown. Expect lower numbers on unseen layouts, multi-line descriptions, discounts/shipping, tax-inclusive totals and noisy scans.
- Rule-based extractor only; no LLM extraction was evaluated (none is wired in). Confidence is heuristic (section 5.5).
- Small samples: 8–16 extraction errors per split; per-type and per-rule figures have wide intervals.
- Speed is from a 1-core Linux sandbox with 1–2 page files. 1,000-page behaviour is in `docs/benchmarks/`; **nothing was measured on the Windows / 8 GB target.**
- Matching of predicted to labeled invoices is by invoice number, falling back to order when counts agree; an OCR-misread number therefore counts as a field error rather than a missed invoice.
- Line-item matching requires description, quantity, unit price and amount all to equal; a row kept with an unreadable quantity counts as one miss and one wrong item (but is flagged `VAL-LINE-003`).
- Cross-document verification was evaluated on 14 synthetic pairs per split (header values only; line items are not compared).
- Semantic search is evaluated separately in `docs/SEMANTIC.md`; it is off in all runs here.
